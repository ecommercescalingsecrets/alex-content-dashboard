🔧 Gethookd Public API — Audit & Fix List

Audited Sep 25, 2026 · Test case: resilia.shop (shop_id 1263) · Base URL https://app.gethookd.ai/api/v1 · Prepared for the Gethookd engineering team
TL;DR: The numbers on the Shop page match the API: traffic, Trustpilot, active ads count, linked pages and products all line up. The real problem is that you can't pull the ads themselves. Resilia shows 8,413 active Meta ads in the dashboard, but the public API returns at most ~1,977 (~23%). For any single brand it returns 50, even when the brand has 2,810. /shops/1263/ads and /shops/1263/analytics return 503 because the shop is still on the legacy (un-published) data path. We also found 9 smaller bugs: a 500, a broken status enum, breakdown truncation, inconsistent pagination, and wrong HTTP codes.

2. P0: Blockers

B-01P0

/shops/{id}/ads returns 503 for legacy (un-published) shops

GET /shops/1263/ads
→ 503 {"errors":true,"message":"Shop ad publication is not available for this shop yet.",
       "data":{"publication":null,"coverage":{"status":"pending_cutover"}}}
Expected
Paginated list of the 8,413 ads shown on the Shop → Meta Ads tab.
Actual
503. /shops/1263 shows ad_publication: null and ad_data_authority: {"source":"legacy","cutover":false}. The UI reads the legacy data; the API won't.
Impact
This hits the biggest shops, the ones customers care about most. Also seen on glovbeauty.com (shop 773, 5,577 ads) and kilgourmd.com (shop 5878, 1,118 ads). Meanwhile the small try.resilia.shop (113 ads) is published.
Fix
Run the publication cutover on every shop with live_ads_count > 0 and ad_publication IS NULL, biggest first. Until cutover is done, serve /ads from the legacy source (the same one the UI uses) instead of returning 503. Add a job/metric that tracks "% of shops (weighted by live ads) published".
B-02P0

Hard 50-ads-per-brand ceiling hides ~98% of big brands' inventory

GET /explore?brand_id=1878084&per_page=50&ads_per_brand_limit=50
→ meta.total = 50, meta.last_page = 50   (brand record says active_ads = 2810)

GET /explore?brand_id=1878084&ads_per_brand_limit=51
→ 422 "The ads per brand limit field must not be greater than 50"

Expected
Filtering by brand_id returns all of that brand's ads, paged normally.
Actual
Stops at 50. meta.total reports 50 rather than the real count, so callers can't tell the list was cut off.
Fix
When brand_id is set, don't apply ads_per_brand_limit (it only makes sense for mixed-brand search results). meta.total should be the true count. Use cursor pagination for large brands. If a cap has to stay, return meta.truncated: true and meta.total_available.
B-03P0

/shops/{id}/analytics returns 503 (same cause as B-01)

GET /shops/1263/analytics
→ 503 "Shop ad publication is not available for this shop yet." coverage.status = "pending_cutover"
Expected
The Active Ads chart data shown on the Shop page (4,358 → 8,413 over time, per page filter).
Actual
503. The API has no way to get the Active Ads time series, even though the dashboard draws it.
Fix
Serve from the same source the UI chart uses. Resolves automatically once B-01's cutover lands.

linked_brand_breakdown silently drops 15 of 49 linked pages

GET /shops/1263/linked-pages
→ linked_brand_count: 49, linked_brand_ids: [49 ids], linked_brand_ids_truncated: false
→ linked_brand_breakdown: 34 entries   ← 15 missing, no flag

(spot-checked 5: Purefield Co., WislowAgatha, Vital Grove, Dr. Michael Rawlings, Herbal Rise, all active_ads = 0)
Fix
Return all 49 rows. Include zero-ad brands with live_ads_count: 0, or add breakdown_excludes_zero: true. The count, id list and breakdown must agree. Anyone building a brand roster currently misses about 30% of linked pages.
B-05P1

GET /ads/latest returns 500 Server Error

GET /ads/latest → 500 {"message":"Server Error"}
Fix
Most likely the route matches /ads/{id} with id="latest" and crashes on a non-integer cast. Add a numeric constraint on {id} (e.g. ->whereNumber('id')) so this returns 404, or implement /ads/latest for real.
B-06P1

/explore status filter: only "active" works; "inactive" returns 0

status=active    → 200 total=13,486,501
status=inactive  → 200 total=0            ← should be millions
status=ACTIVE | Active | paused | 1 | 0 | true | false → 422 "The selected status is invalid."
Fix
Wire inactive to the inactive corpus, or remove it from the allowed enum and document that only active ads are indexed. Put the valid values in the 422 message, e.g. "status must be one of: active, inactive".
B-07P1

Growth % drift between UI card and API

UI:  "+33.8% active ads growth"
API: active_ads_growth_pct = 35.48
Fix
Point the UI card and the API field at the same stored value, or expose the value and its computed-at timestamp so the two can be reconciled. The same staleness is explained in meta.count_basis prose for live_ads_count. Make it machine-readable (meta.as_of per field, or an X-Data-As-Of header).

4. P2: API contract / consistency

B-09P2

Unknown routes return 405 "Method not allowed" instead of 404

GET /me, /user, /account, /folders, /swipes, /swipe-files, /ads, /search, /discover,
    /countries, /languages, /platforms, /formats, /trends, /leaderboard,
    /brands/{id}/ads, /brands/{id}/stats, /brands/{id}/analytics,
    /shops/{id}/brands, /shops/{id}/pages, /shops/{id}/stats, /shops/{id}/summary,
    /niches/{id}/brands, /niches/{id}/shops, /nope   → all 405
Fix
405 means "the resource exists but not with this method". These resources don't exist, so return 404. This looks like a catch-all fallback route that returns 405. Change the fallback handler to 404.
B-10P2

Non-existent IDs return 200 with empty data

GET /explore?brand_id=999999999 → 200 {"data":[]}
Fix
Validate the ID exists (exists:brands,id) and return 422 "brand_id not found". Callers currently can't tell "brand has no ads" apart from "wrong ID".
B-11P2

/explore filter set is much thinner than the UI's

Only 10 params are accepted: query, brand_id, page, per_page, niche, language, platform, status, has_transcript, ads_per_brand_limit. About 80 common ones return 422, including the ones the dashboard filters on:

shop_id, domain, landing_domain, landing_page, page_id (FB), country, created_after,
created_before, min_days_active, asset_type, format, ids, tags, sort, order
Fix
Priority adds: shop_id (needed to work around B-01/B-02), landing_domain, country, asset_type, min_days_active, created_after/before, sort (days_active|created_at|last_seen), ids[] (batch lookup).
B-12P3

Missing brand-scoped resources + encoding bug

  • /brands/{id}/ads returns 405. Consumers have to use /explore?brand_id= instead, which is capped (B-02). Add a real brand ads endpoint with no per-brand cap.
  • Tagline mojibake: "ResiliaÂ® offers…" (UTF-8 decoded as Latin-1 during scrape). Shows up in /shops/1263 and /shops/1263/similar. It also appears on the dashboard itself ("ResiliaÂ®").
  • /shops/1263/similar wraps its list in data.similar_shops while every other list endpoint uses data: [...]. Keep the envelope consistent.
  • /shops/{id} has social_handles: [] even though Resilia has 49 linked FB pages. Populate from linked pages.
